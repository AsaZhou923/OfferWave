# ADR-0001：v1 采用邮箱优先认证

- 状态：已接受
- 决策日期：2026-08-11
- 适用版本：OfferWave v1

## 背景

2026-02-12 的《需求规格说明书》草案描述了微信登录，但 2026-03 之后的实现、README、API 与版本记录已经形成完整的邮箱认证路径：

- 邮箱 + 密码注册/登录；
- 邮箱验证码登录；
- 邮箱验证码重置密码；
- JWT 作为 API 访问凭据。

审查时仅有未使用的微信运行配置和历史 `wechat_openid` 数据字段，没有微信授权回调、账号绑定、隐私告知或相关测试。继续同时把两种方案写成“当前能力”会造成产品、客户端和安全边界不一致。

## 决策

OfferWave v1 的唯一正式认证方案是邮箱优先认证：

1. 注册使用邮箱、密码和邮箱验证码；
2. 登录支持邮箱/用户名 + 密码，以及已注册邮箱 + 验证码；
3. API 只接受 `Authorization: Bearer <JWT>`；
4. 微信登录不属于 v1 已承诺能力，配置与接口文档不再保留占位描述。

原需求规格说明书保留为历史输入；本 ADR 对 v1 认证方案具有更高优先级。

## 安全约束

- 验证码必须限时、限制失败尝试并原子单次消费；
- 发送验证码的外部响应不得泄露账号是否存在；
- 密码重置后应撤销此前签发的令牌；
- JWT 密钥必须由部署环境提供，不允许公开或弱默认值；
- Token 只允许通过标准 Bearer Header 传输。

## 后果

- README、API 文档、运行配置和测试以邮箱认证为准；
- 未实现的微信运行配置/API 占位已删除；历史 schema 字段暂留用于既有数据库兼容，不代表 v1 对外能力；
- 如果未来引入微信登录，必须新增独立 ADR，覆盖 OAuth 回调、账号绑定/解绑、冲突合并、隐私同意、令牌撤销与回归测试；
- 在上述设计完成前，不得重新加入仅有 `appid/secret` 的“占位支持”。
